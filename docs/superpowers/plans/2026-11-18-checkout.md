# Restore storefront checkout

The static storefront must be able to submit its local cart and show an accurate payment result. Preserve the embedded Stripe flow, older saved cart identifiers, existing order records and the single supported standard rate from the cart.

- Validate cart, email and discount inputs at the API boundary. Resolve legacy single-variant lines and current variant identifiers against active database products. Use server prices and reserve stock and discount uses together with the pending order.
- Create Stripe Checkout with the embedded return URL, the server shipping rate and Stripe discounts. Retries with the same checkout identifier reuse the order and Stripe idempotency keys. Keep reservations when the result of a Stripe request is unknown.
- Settle reservations from Stripe-signed events in one database transaction. A duplicate event must preserve inventory and order state. Release stock and coupon reservations on a verified expiration or failed payment. Preserve legacy paid-event support while rejecting incomplete legacy line data.
- Show the order number and total only after payment is confirmed by the backend. Remove only the quantities submitted in that browser’s confirmed cart. Keep the checkout and order routes out of search results.
- Exercise the public routes with a disposable PostgreSQL database and a Stripe test double. Check that test-mode credentials are complete before attempting an external test checkout. Production deployment, real charges and production data changes are separate actions.

## Verification and staging

- All 17 regression tests passed with PostgreSQL 14 in a disposable local database and Stripe calls handled by a test double. The tests covered server pricing, insufficient stock, limited-use discounts, an interrupted Stripe response, retries, concurrent payment notifications, changed totals and expired sessions.
- Production build, static export and a mobile confirmation check passed. Confirming an order removed only the purchased quantities from the browser cart, including after a reload. The rendered sitemap still contains 180 canonical pages and 107 eligible guides.
- Staging requires a matching Stripe test secret key and public key, a signing secret for that environment, and an isolated database with `order_number_seq`. The Stripe endpoint subscribes to `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, and `checkout.session.expired`. Set `CHECKOUT_STOREFRONT_ORIGIN` on the backend when the storefront under test uses an origin separate from the public canonical domain.
- When Stripe has no confirmed result, repeating the same checkout uses the original order reference. If an interrupted request leaves a pending reservation that cannot be retried through checkout, reconcile its order reference with Stripe before releasing stock. A verified expired session releases its stock and discount use.
- The public sitemap was reachable and contained 112 URLs, including 63 guides and zero journal topic pages. The worktree has not been deployed. The local environment lacks a complete set of Stripe test-mode credentials for an end-to-end Stripe Checkout attempt.
